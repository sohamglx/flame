The `std.web` module is Flame's official framework and compiler toolchain for building high-performance, reactive web applications.

Instead of shipping a heavy runtime framework or forcing bulky WebAssembly binaries for simple UI updates, Flame compiles your UI and component declarations directly into **clean, fine-grained reactive JavaScript, HTML5, and CSS**.

---

## Architectural Philosophy: Polyglot Compilation

The browser's user interface is fundamentally a JavaScript and DOM environment. Access to the DOM tree, events, animations, and Web APIs are native to browser JavaScript engines.

Flame cleanly divides responsibilities between JavaScript and WebAssembly (WASM):

```text
                 Flame Source (*.fm)
                          │
                        Blaze
                          │
                     @Web Target
                          │
              ┌───────────┴───────────┐
              │                       │
          UI / DOM               Computation
              │                       │
         JavaScript                  WASM
              │                       │
              └───────────┬───────────┘
                          ↓
                   Modern Browser
```

- **UI & DOM Manipulation**: Compiles to minimal, human-readable JavaScript with direct DOM node updates.
- **Browser APIs**: Maps 1:1 with native browser globals (`window`, `document`, `localStorage`).
- **Networking**: Idiomatic `std.net.http` client compiled to high-speed asynchronous requests.
- **Zero Heavy Runtimes**: Output bundle `dist/app.js` is typically under **2 KB** before minification!

---

## Fine-Grained Reactivity (No Virtual DOM)

Unlike traditional frameworks like React that re-render entire component functions and perform expensive virtual DOM tree diffing on every state change, Flame's compiler performs **fine-grained static dependency tracking**:

### React Virtual DOM vs. Flame Compiler Updates

```text
React (Runtime Overhead):
state change ──> re-render component ──> allocate virtual DOM ──> tree diffing ──> DOM mutation

Flame (Zero Virtual DOM):
state change ──> known compiler dependency ──> direct DOM node update
```

Because Flame knows statically which text nodes and attributes reference `@State` variables, generated JavaScript modifies **only the exact affected DOM text node or attribute**:

```text
count changes ──> _t0.textContent = "Counter: " + count
```

The surrounding `<main>`, `<h1>`, and `<button>` elements are untouched, and no component re-renders take place.

## Multi-File Project Architecture

Large web applications should be modular. Flame provides native multi-file support with automatic file discovery, modular imports/exports, tag-like component instantiation, and auto-registered routing.

### Directory Structure

A typical multi-file Flame web project is structured as follows:

```text
my-web-app/
├── flame.toml             # Project manifest
├── src/
│   ├── main.fm           # App entrypoint (@Web, @Layout, root @Page("/"))
│   ├── navbar.fm         # Shared navigation bar (export @Component fn NavBar)
│   ├── about.fm          # About page (export @Page("/about") fn about)
│   ├── projects.fm       # Projects page + API fetching (export @Page("/projects"))
│   └── contact.fm        # Contact form (export @Page("/contact") fn contact)
└── dist/                 # Auto-generated static web bundle
    ├── index.html        # HTML5 entry mounting to #app
    ├── app.js            # Standalone reactive signals + SPA router + compiled UI
    └── app.css           # Preserved custom stylesheet + @Style injections
```

### Automatic File Discovery & Bundling

When compiling or running a web project (`flame run --web` or `flame build --web`), Flame's compiler:
1. Automatically scans the entire `src/` directory recursively for all `.fm` and `.flame` source files.
2. Processes all exported declarations (`export @Component`, `export @Page`, `export fn`).
3. Seamlessly links modular dependencies (`import navbar`, `import about`, etc.) without requiring external bundlers like Webpack, Vite, or Rollup.

## Exports, Components & Auto-Routing

Flame enables seamless modularity through the `export` keyword:

### 1. Reusable Tag Components (`export @Component`)

Declare reusable UI components in dedicated files with `export @Component`:

```flame
// src/navbar.fm
import std.web

export @Component
fn NavBar() {
    <header class="navbar">
        <div class="nav-brand">⚡ Flame Web</div>
        <nav class="nav-links">
            <a href="/" class="nav-link">Home</a>
            <a href="/about" class="nav-link">About</a>
            <a href="/projects" class="nav-link">Projects</a>
            <a href="/contact" class="nav-link">Contact</a>
        </nav>
    </header>
}
```

Once imported, components can be rendered anywhere in your UI like standard tags:
```flame
<NavBar />
```

### 2. Auto-Integrated SPA Routing (`export @Page`)

In Flame, any function annotated with `export @Page("/path")` in any `.fm` file in `src/` is **automatically registered into the client-side SPA router**:

```flame
// src/about.fm
import std.web
import navbar

export @Page("/about")
fn about() {
    <div class="page-container">
        <main class="content-section">
            <h1 class="section-title">About Flame Web</h1>
            <p>Fine-grained reactivity with zero virtual DOM.</p>
        </main>
    </div>
}
```

<Aside type="tip" title="Zero Route Boilerplate">
You do not need to configure an explicit route table or router object in `main.fm`. Simply exporting `@Page("/about")` causes Flame's compiler to register `/about` into the router and link navigation from any `<a href="/about">` tag automatically.
</Aside>

### 3. Pages Usable as Tag-Like Components

Every `@Page` is also registered as a reusable component. You can mount a page directly inside another component or layout:

```flame
<About />
```

## App Shells with `@Layout`

Web applications often require a consistent layout shell (such as a top navigation bar, sidebar, and footer) that wraps all page content.

Flame provides the `@Layout` annotation:

```flame
// src/main.fm
@Layout
fn AppLayout(children) {
    <div class="app-layout">
        <NavBar />
        <div class="app-content">
            {children}
        </div>
    </div>
}
```

### How `@Layout` Works
- **Automatic Wrapping**: Pages that do not specify a custom layout are automatically wrapped inside the `@Layout` component.
- **Dynamic Slot Interpolation**: The `{children}` expression automatically injects the active `@Page` content into the layout container.
- **Persistent Chrome**: When switching routes via the client-side router, the layout shell remains intact while only the `{children}` DOM node updates.

## Networking & Asynchronous Functions (`std.net.http`)

Flame Web projects use Flame's native networking module `std.net.http` rather than browser-specific APIs:

```flame
import std.net.http

export fn fetchProjects() {
    let container = web.document.getElementById("projects-grid")
    if container {
        container.innerHTML = "<div class='loading'>Loading live projects...</div>"
    }

    // High-level HTTP GET request with await
    let data = await http.get("https://jsonplaceholder.typicode.com/posts")

    if container {
        container.innerHTML = ""
        let mut i = 0
        while i < 6 && i < data.length {
            let post = data[i]
            let card = web.document.createElement("div")
            card.className = "project-card"
            card.innerHTML = "<h3>" + post.title + "</h3><p>" + post.body + "</p>"
            container.appendChild(card)
            i += 1
        }
    }
}
```

### Automatic `async function` Generation
Flame's compiler performs static AST analysis to detect any use of `await` inside functions, components, event handlers, and closures. When `await` is present, Flame automatically marks the compiled JavaScript declaration as `async function`:

```javascript
// Compiled output in dist/app.js
async function fetchProjects() {
    // ...
    let data = await http.get("https://jsonplaceholder.typicode.com/posts");
    // ...
}
```

This ensures full compliance with JavaScript syntax specifications and prevents browser `SyntaxError: Unexpected reserved word` errors.

## Running and Developing Web Applications

Flame provides a built-in HTTP server, live-reload watcher, and static bundler:

### 1. Development Server (`run --web`)

Start a local development server:

```bash
fmp run --web src/main.fm
```

This compiles your project into `dist/` and serves it at `http://localhost:3000/`.

### 2. Live Hot Reload (`run --watch --web`)

Enable hot reloading during active development:

```bash
fmp run --watch --web src/main.fm
```

The watcher listens for filesystem changes across your source files, automatically recompiles `dist/app.js` and `dist/app.css`, and immediately refreshes the browser without losing scroll state.

### 3. Production Build (`build --web`)

Generate an optimized static distribution:

```bash
fmp build --web src/main.fm
```

## Anatomy of the `dist/` Output

When Flame builds your web application, it produces a self-contained static directory ready for instant deployment:

```text
dist/
├── index.html   # HTML5 entry point mounting the app to #app
├── app.js       # Standalone reactive runtime, router, and compiled UI (<2 KB)
└── app.css      # Merged styles (custom styles preserved + @Style injections)
```

### Stylesheet Preservation
When you customize `dist/app.css`, subsequent `flame build --web` or `flame run --web` runs **never overwrite** your custom CSS rules. Instead, Flame merges custom CSS with any `@Style` declarations in your code.

## Core Annotations Reference

| Annotation | Target | Description |
| :--- | :--- | :--- |
| `@Web` | `fn main()` | Marks the application entrypoint. Accepts optional parameters `title` and `port` (e.g. `@Web(title: "My App", port: 3000)`). |
| `@Layout` | Function | Declares an application shell wrapping page content. Receives `(children)` as parameter. |
| `@Page(path)` | Function | Declares a client-side routable page (e.g. `@Page("/")`, `@Page("/about")`). Automatically integrated into the SPA router. |
| `@Component` | Function | Declares a reusable UI component that returns JSX elements. Usable as a tag (`<NavBar />`). |
| `@State` | `let mut var` | Marks a variable as reactive. Compiles to an observable signal; mutations instantly update dependent DOM nodes. |
| `@Style` | Function | Injects CSS rules into `dist/app.css` without overwriting existing stylesheet content. |

## JSX Syntax Rules & Behavior

### Clean Text Handling
Text placed inside JSX tags behaves as plain text:

```flame
<p>Compile Flame's source directly into high-speed native JavaScript.</p>
```

- Plain words are treated as text content without erroneous keyword or function highlighting.
- Apostrophes (such as in `Flame's`) do not break strings across lines or create unwanted auto-closing quote pairs.

### Expression Interpolation `{expr}`
Dynamic Flame code is placed inside curly braces:

```flame
<h1>Counter: {count}</h1>
```

### Event Handlers (`onClick`, `onInput`, `onChange`, `onKeyDown`)
JSX attributes starting with `on` register native DOM event listeners:

1. **Inline Signal Mutations**:
   ```flame
   <button onClick={count += 1}>Increment</button>
   ```

2. **Function References**:
   ```flame
   <button onClick={fetchProjects}>Fetch Data</button>
   ```

3. **Multi-Statement Event Blocks**:
   ```flame
   <button onClick={
       count += 1
       toggleColor()
   }>
       Update
   </button>
   ```

### Dynamic Inline Styles
Use curly braces with dynamic string expressions:

```flame
<button style={"background-color: " + btn_color + "; color: white;"}>
    Active Color: {btn_color}
</button>
```

## Deploying to Production

Deploying your Flame Web application is as simple as hosting the `dist/` directory on any static cloud provider:

<CardGrid>
  <Card title="Cloudflare Pages">
    - **Build Command**: `fmp build --web`
    - **Output Directory**: `dist`
  </Card>
  <Card title="Vercel">
    - **Framework Preset**: Other
    - **Build Command**: `fmp build --web`
    - **Output Directory**: `dist`
  </Card>
  <Card title="Netlify">
    - **Publish Directory**: `dist`
    - **Build Command**: `fmp build --web`
  </Card>
  <Card title="Docker / Nginx">
    - Copy `dist/` directly into `/usr/share/nginx/html`
    - Supports instant caching and sub-millisecond edge delivery.
  </Card>
</CardGrid>
